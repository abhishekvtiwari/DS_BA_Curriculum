# 2 October 2026 · Section 71.11, the predict-the-output round

**Why.** Abhishek's instruction: Book 4 is the product's main selling point, and the interview
material has to be ground down "from very basic to very detailed one," with brain-racking
output-prediction questions — the example given was `int("25", 4)`.

Measured first, across the whole of Part VIII: 619 questions, of which **19** were
output-prediction, and **17 of those 19 sat in one section**, Chapter 72's §72.2. Thirteen of the
fourteen banks had none at all. §72.2 was therefore taken as the proven in-book format, and
Chapter 71 was built first as the template for the rest, the way Chapter 37's notebook served as
the template for the practice material.

## What was added

**Section 71.11, "Predict the output: from basic to brain-racking."** 10,050 words. 16 core
questions (Q71-077–092) and 16 rapid-fire rows in two tables (Q71-093–108), taking the chapter
from 76 questions to 108. Nothing was renumbered: sections 71.1–71.10 are cited by number from
other chapters, and the new section appends after 71.10, the same reasoning recorded for Chapter
18's new sections. The codes continue from 076, where the earlier renumbering map in this file
ends.

A fourth level, **Brain-racking**, sits above Warm-up/Core/Advanced for five of the questions.
The section carries its own levels per question rather than inheriting one from the section,
because it deliberately runs the full range; the at-a-glance box now says so.

| Level | Questions |
|---|---|
| Warm-up | Q71-077, Q71-078 |
| Core | Q71-079–086, Q71-092 |
| Brain-racking | Q71-087, Q71-088, Q71-089, Q71-090, Q71-091 |

Every question keeps the chapter's established shape: a **Remember it as** hook, a one-line

The questions turn on three mechanisms rather than twenty unrelated tricks: NULL is not a value

## Verification, and what is still outstanding

`companion/riverstone_2025_setup.sql`, loaded into DuckDB — chosen after confirming it reproduces

the corrected answer 2, and 1 of 24 customers with no orders. The loader strips `FOREIGN KEY`
clauses, because DuckDB checks them per row and the self-referencing `employees.manager_id` fails
there although PostgreSQL accepts it; the constraints are not what any of these questions test.

**Outstanding: the confirming run on PostgreSQL 16 and MySQL 8.4.** Neither is installed in this
environment. The chapter's at-a-glance box now states this exception rather than letting the new

labelled **Run (riverstone_2025)** rather than **Verified**. Four questions are marked **Dialect

## Questions the runs killed or changed

Recording these because the first drafts of each were wrong, and the only reason they are not in
the book is that the queries were run:

1. **`customers.city` has no NULLs in `riverstone_2025`.** The full dataset has 100, the 24-row
   practice database has none. Three drafted questions aimed at it — a `<>` arithmetic trap, a
   NULL-concatenation trap and a NULL-ordering question — were dead on this data and were
   retargeted onto `orders.sales_rep_id` (11 NULLs) and `employees.manager_id` (1).
2. **The `BETWEEN` on a timestamp trap does not fire on Riverstone.** `orders.order_date` is a
   `DATE`, so the inclusive and half-open forms both return 8 for January. Rather than drop the
   point or fake it, Q71-108 states that the column's type is why the bug survives review
   elsewhere, which is the more useful lesson.
3. **Q71-104 was wrong in draft.** The three months tied on 13 orders are not the lowest group, so
   `RANK` gives 4, 4, 4 and not 1, 1, 1. Corrected, and the `RANK`/`DENSE_RANK` divergence after
   the tie (7 against 5) added.
4. **Q71-090's `0` is PostgreSQL's answer, not a run.** DuckDB does not truncate integer division,
   so it returns 0.0114 where PostgreSQL returns 0. That output is now labelled PostgreSQL 16,
   with MySQL's different-but-also-wrong 0.0114 described beside it.
5. **Q71-102's row order is arbitrary.** Hospitality and Retail both have 9 customers, so
   `ORDER BY 2 DESC` does not determine which comes first. The row now says so and points at
   Q71-088.
6. **Q71-087's ROWS column needed a tiebreak to be reproducible.** With `ORDER BY orders` alone
   the `RANGE` column is stable (68 for all three tied months) but the per-row `ROWS` assignment
   is engine-determined. Each of the three variants was run five times and only the stable ones
   are printed; the instability is itself the last part of the question.

# 3 October 2026 · Book 4 rebuilt, and what it took to build anything on this machine

Chapter 71 grew by about 10,000 words on 2 October, so Book 4 was out of date. Rebuilding it
needed three fixes to the build environment first, none of them to the build's logic.

## Three things stopped the build running here

1. **No pandoc.** `tools/pdf/build.py` shells out to `pandoc`, and there is no system pandoc on
   this machine. Installed `pypandoc-binary`, which ships pandoc 3.9 in the wheel, and added
   `tools/review-export/build_book.py` to put it on PATH for the build. Nothing in the build
   changed.

2. **cp1252.** `build.py` calls `read_text()` and `write_text()` without naming an encoding. On
   Linux that means UTF-8; on Windows it means cp1252, and the manuscript has characters cp1252
   cannot decode, so every chapter failed to read. The same runner sets Python's UTF-8 mode.

3. **A hard-coded font path.** `FOOT_FONT` pointed at
   `/usr/share/fonts/truetype/dejavu/DejaVuSans.ttf`, which exists only in the sandbox the build
   was written in. It now resolves through a list of candidates and finds the identical font file
   that ships with matplotlib, so the footers render exactly as before. `BOOK_FOOT_FONT`
   overrides. **This is the only change to a file under `tools/pdf/`.**

## Why only Book 4 was rebuilt

Before rebuilding anything else, Book 1 was rebuilt as a test and compared against the shipped
PDF. It came out **217 pages against 218**, with 203 of 217 pages differing. The first difference
is on the cover: `A N A L Y S T` against `A N A LY S T`. The fonts resolve differently on this
machine, so the rebuild is not reproducible here, and rebuilding Books 1 to 3 would have
re-paginated three unchanged books for no content reason and invalidated every visual finding that
cites a page in them.

So only Book 4, whose content actually changed, was rebuilt.

**A consequence worth stating:** Book 4's pagination moved slightly more than the new section alone
explains. Chapter 69 moved one page and Chapter 70 two, although neither changed. That is the same
font effect. **Book 4's visual check should be redone before release.**

## The series map

Building Book 4 alone does not produce the series map, because `books.py map` needs all four
books' page data, and `*-heads.json` is not committed.

Rather than rebuild everything, the map was reconstructed: Books 1 to 3 rows taken from the
existing map verbatim, since those books did not change, and Book 4's eighteen rows recomputed
from the new build. The page numbers are read from the **footer printed on each page**, not from
the PDF page labels, which in the rebuilt Book 4 read three higher than the printed number.

The extraction is self-checked: run over the *old* Book 4 it reproduces that book's own map rows
**18 of 18**, and the script refuses to write a new map if it does not. The three map pages are
appended at the back, where the shipped book has them, with the `The whole book` bookmark.
