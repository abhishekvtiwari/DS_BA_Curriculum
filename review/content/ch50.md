# Ch 50 — Streaming & Real-Time
Verdict: A mature, honest chapter. It asks "is this worth doing in real time?" before building anything, it has a runnable local log that teaches partitions, offsets, groups and at-least-once without a broker, it reproduces real Spark watermark behaviour (empty first batch, 456 = 450 + 6, stragglers dropped), and it has a good "streaming for speed, batch for truth" design. The window counts and watermark arithmetic check out. For a first-time reader there are four big problems. (1) The by-hand foundations the brief requires are missing or wrong. Figure 50.1 puts M-03 and M-12 in *both* partitions, which contradicts the chapter's key rule. Figure 50.2 says window 00:05–00:10 closes at watermark 00:09:50, which is false and contradicted by the output. The "Reading it" after the progress cell has the watermark moving to 00:09:50 when it moved *to* 00:19:50. Sliding and session windows and at-most-once exist only as parentheses or prose, with no timeline. (2) The companion helpers are black boxes. `se.batch(600, …)` returns 300 events and `se.batch(50, …)` returns 6, and the comment says "first minute" for two minutes of data. (3) Code blocks are dense: the windowed query brings ~12 new Spark ideas at once, and the Kafka block ~15, with undefined `events`/`handle`. (4) The de-duplication "fix" keeps its `seen` set in memory, so a real crash would empty it and the duplicates would come back. "Watermark" also clashes with Ch 45's incremental-load watermark, and nothing says so.
Size: ~840 lines, 21 book pages (139–159), 11 code blocks (1 not executed), 14 exercises, a 9-step project. Time needed stated: 12–16 hours over two to three weeks; plausible? Yes for reading + code + exercises (~6–7 h), but tight with the 9-step project (alerting consumer, crash test, streaming job, correction path, monitoring plan, memo ≈ 8–10 h). Adding the by-hand timelines below adds ~1 h, so state 14–18 hours.

## What works (keep)
- §50.1's latency table and three questions (what decision changes, cost of being late, who watches it), plus "Watch out: a real-time dashboard is usually a batch job with a shorter schedule". This is architect-level judgment put simply.
- Choosing `mini_log.py` over requiring a broker, while still showing real `kafka-python` code marked "not executed", is the right call for a practice environment. The crash-before-commit demo (82 alerts sent twice, then 0 with a key) makes at-least-once concrete.
- The three windowed runs are real Spark semantics and the numbers are right: append mode emits nothing while the watermark is 23:59:50; the six M-07 stragglers are folded in (15 machines × 6/min × 5 min = 450, + 6 = 456; Chakan 10 × 30 = 300); the M-09 stragglers are dropped at watermark 00:09:50; windows up to 00:10–00:15 are emitted at 00:19:50; state holds 10 rows (5 open windows × 2 plants). Answers 6 and 7 state the watermark rule correctly.
- §50.8 (alert path / aggregation path / daily correction) and "the alert that cried wolf" (1,900 → 11 alerts; windows, de-dup, per-machine limits) connect the tech to a decision and a person.
