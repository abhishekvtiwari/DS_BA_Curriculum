# Ch 47 — Data Quality, Observability & Contracts
Verdict: A strong, well-motivated chapter. The "a test is a query that returns failing rows" idea, breaking the suite on purpose, write–audit–publish on the same 5 January failure as Ch 46, and the incident and alert-fatigue material are all excellent, and the story threads cleanly out of Ch 45–46 (177 → 178 orders, ₹38,710 and ₹18,750 all agree with Ch 46). For a first-time reader, four problems stand out. (1) The code arrives in large blocks with thin explanations. The WAP block does about eight new things at once, and the freshness, lineage, contract and alert functions get only a paragraph each. (2) The freshness arithmetic is wrong for date columns: yesterday's data is already 30.5 h old at 6:30 a.m. So the "under 24 hours" promise, the "48 hours allows for weekends" claim (a Monday run is 78.5 h), the real-world "24 hours" fix and the Ex 8 answer (26 h, "no Sunday orders") would all fail or contradict the data. (3) The reconciliation test compares a DuckDB DOUBLE with a DECIMAL(12,2) using `<>`, which I verified on DuckDB 1.5.5 and which will falsely block publication on real discount data. (4) Great Expectations and Soda are promised (the chapter goals, and Ch 14 "Chapter 47: … dbt tests, Great Expectations") but appear only in a table. The dbt YAML also uses the old `tests:` syntax, while Ch 32 taught `data_tests:` + `arguments:`.
Size: 1,196 lines, about 28 book pages (69–96), 12 code blocks plus 3 in the answers, 14 exercises. Time needed stated: 12–16 hours over two to three weeks; plausible? Yes for the current text. With the proposed splitting of blocks and the added cells (fix-and-republish, upstream lineage, contract value checks, optional GE/Soda box), it becomes about 14–18 hours. Restate it as 14–18 hours, in four sittings: 47.1–47.3; 47.4; 47.5–47.7; 47.8–47.10 and the project.

## What works (keep)
- §47.2's one-line principle ("Write a query that returns the rows that break the rule… zero rows means pass") is the right mental model. It carries the whole chapter, and it matches how dbt generic tests compile.
- "Watching them fail" (§47.3) is exemplary. The ERP's foreign key refuses the orphan line (a real Postgres error message is shown), the warehouse accepts it, three different tests catch three different breakages, and a hash-comparison resync repairs all three. It ties Ch 12, Ch 45 and Ch 46 together, with outputs that agree (7 tests → 4 passed, 3 errors → 7 passed).
- WAP replaying Ch 46's exact 5 January failure (ERP 1 order / ₹18,750.00 vs warehouse 0 / ₹0.0), followed by "readers of mart.daily_flash never saw the 5 January row: True", is a very clear before/after. So is the "missing day looks like a zero day" Watch out.
- §47.8–47.9 (the incident severity table, the user-facing message wording, "communication at containment") and the real-world "right but late" story (the failure alert was message seven of twelve) teach professional habits that most books skip.
