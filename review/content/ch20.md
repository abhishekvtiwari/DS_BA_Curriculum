# Ch 20 — Automating Reports & Delivering Insights
Verdict: The best-judged chapter of the three on *what* to do. It covers the automation ladder, mapping and timing the flow, "put the answer in the body", report versus alert, checks before sending, the "no data" branch, idempotency, recipients and confidentiality, and handover. The flash-that-stopped story is excellent. It is weakest on *how*:
- Several techniques are shown in a form that fails in practice. The base64 chart is blocked by Gmail and by Outlook desktop. The Task Scheduler action has a fixed date, so it would send 18 December every day. Cron and Windows jobs run in the server's time zone, with no instruction to set IST.
- The whole `daily_flash.py` is never shown, so the reader never sees the try/except failure alert, the `--send` flag or the "no data" branch in code.
- SMTP, HTML, python-dotenv and the shell syntax used in cron are used without being taught.
- A few numbers and cross-references are wrong.
Size: ~820 lines, ~19 pages (343–361), Time needed stated: 18–22 hours over two to three weeks; plausible? Yes. The chapter is mostly prose. The project needs a mail account, a scheduler and a database, so add 2–4 hours for setup if the recommended SMTP test server, `.env` and full-script walkthrough are added.

## What works (keep)
- 20.1 ladder and 20.2 flow map with timed steps ("automate the 80 minutes, keep the 3 sentences"). This is a clear, reusable method.
- 20.4 "An attachment is a request; a body is an answer" and 20.5's six design rules for the email body.
- 20.8 report vs alert, and thresholds that survive reality (history, persistence, materiality, action, count them). 20.11 checks, failure alert, "no data today", retries, idempotency with a run key.
- 20.12 recipients and confidentiality, and 20.13's seven-heading handover note. The real-world story ties the checks to a failure the reader will remember.
