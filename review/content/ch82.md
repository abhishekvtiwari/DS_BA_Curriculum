# Ch 82 — Take-Home Assignments & Mock Interviews
Verdict: The format is right: an assignment as given, a model submission, a scoring table, what weak looks like, and a scored mock. The DA and DE submissions model good habits (fixing the grain, a caveat, an upsert, a named second check). But the model submissions aren't as "verified" as claimed.
- **DA:** the recommendation is revenue-only, and the book's own margins (Ch 4, Ch 12) show Industrial earns no more gross profit per order than Storage or Kitchen. It also never answers the "growth" question it was asked.
- **DS:** it stitches together numbers from three different models and two datasets (the Ch 37 *churn* AUCs, and the Ch 36/39 logistic *lead* model's confusion matrix and profit curve) under one "gradient-boosted" label. It claims "over twice the value for the same team capacity" when the baseline works 3.5× as many leads.
- **DE:** the SQL is valid PostgreSQL 16 (run on a toy copy of the schema), but it isn't fully re-runnable (CREATE TABLE fails on the second run), leaves stale rows, and its quality check can't fail anything.
- **Leftovers and pointers:** "blueprint"/"this chat" and a literal `<!-- db -->` remain in the text. Every "Learn it in" points to a question bank rather than the teaching chapter.

Size: ~400 lines / 11 pages (263–273). Time needed stated: none; plausible? Needs adding: the take-homes alone are 2 + 3 + 2 hours timed, so about 10–12 hours with review and one recorded mock.

## What works (keep)
- §82.1 Step 2 names and fixes a real grain error ("averaged per order line, not per actual order"). The Furniture n = 2 flag ("rather than either ranking it seriously or dismissing it") is exactly the honesty Ch 22 teaches.
- §82.3's design note: idempotency explained in one sentence, "fail loudly", and a volume-anomaly check with the right reason (a truncated file passes a negative-revenue check). It matches Ch 47 §47.5.
- §82.4 mock: the clarifying question about "last 90 days from today vs. from the latest date" is excellent. The NOT IN / NULL pre-emption reproduces correctly (without `customer_id IS NOT NULL`, a NULL in the subquery returns 0 rows; verified).
- §82.6 mock: "fail loudly if an expected column is missing, rather than defaulting silently, that's the actual root cause, not the rename" is the right systemic answer. So is "batch because the decision is daily".
