# Ch 46 — Pipelines & Orchestration
Verdict: The design teaching is excellent and matches senior practice. It covers dependency graphs that limit damage, partition overwrite in a transaction, a delivery log with a content hash, backfills that don't re-send, blocking checks before any side effect, and actionable alerts. The "bad morning" story is memorable. The executable part has serious problems for a first-time reader, though. (1) The mock CRM API is shut down at the end of §46.5, so every later run's CRM step fails. As a result, §46.6's retry output contradicts its own prose (the output shows "run succeeded: False"), and §46.7's prose claims "raw_crm_leads succeeded" while the output lists it as a failed step. (2) Installation is one line (`pip install dagster`), and that line doesn't install the web server that `dagster dev` needs; the "save it to a file and run dagster dev" instruction would also wipe the warehouse and clash over the DuckDB file lock. (3) `ingest.py`, which every asset calls, is never shown. (4) Several claims don't match the code or the tool: which day the 6:30 schedule builds, that assets "use the partition date" (the ingestion assets ignore it), and the backfill figure and text. Sensor and DAG are not built from a small example first.
Size: 1,318 extracted lines, 32 pages (pp. 37–68 of Part V). Time needed stated: 14–18 hours over two to three weeks. Plausible? Roughly. Once the install, a real definitions file for `dagster dev`, the `ingest.py` walkthrough, a sensor example and the smaller code cells are added, 16–20 hours is more honest. State four sittings: §46.1–46.3 (ideas, first run); §46.4–46.5 (idempotency, backfills, late data); §46.6–46.7 (retries, checks, alerts); §46.8–46.10 plus the project.

## What works (keep)
- Figure 46.1 plus the §46.7 bad morning. The dispatch failure doesn't stop the Flash because it isn't a dependency, and the empty order-line load is caught only by the reconciliation check ("Checks catch the failures that don't crash"). This is the best single lesson in Part V.
- §46.4's deliberate failure test. The append step doubles revenue to ₹77,420 (the arithmetic checks out), and Figure 46.2 sets the two designs side by side. The idempotency pattern table (partition overwrite, upsert, swap, delivery log, idempotency keys) is complete and practical.
- The delivery log keyed on a content hash, with labeled corrections, and "rebuild history, don't re-deliver it" for backfills. Answer 7 honestly exposes the design's own gap: it compares against any past delivery, not the latest.
- §46.8's Dagster ↔ Airflow mapping table and the "logical date is the start of the interval" Watch-out; §46.10's operating habits (owner, SLA, runbook).
