# Ch 49 — Storage, Warehouses & Lakehouses
Verdict: One of Part V's strongest chapters. It measures claims instead of asserting them (sizes, Parquet metadata, a real Delta log, an atomic correction, time travel, compaction), and the closing story makes the value of a transaction log easy to feel. For a first-time reader it has three serious problems. First, the §49.8 cost estimate is off by a factor of 365 ("126 million readings a day-equivalent" is really 126 million a year, which is 0.76 GB, not 277 GB), and the dollar amounts are mangled into LaTeX ("0.023perGB − month(typical…)"). Second, the compaction demo appends the same 9,000 rows 24 times, so its "merged data compresses better" result (2.73 → 0.53 MB) comes mostly from duplicate data. Third, several technical explanations are wrong: temperature_c "every value differs" (it is dictionary-encoded with at most about 5,300 distinct values), "0.80 MB on disk" (that is the uncompressed size), ACID "Consistency" illustrated with an atomicity failure, and "Chapter 12 introduced these" (Chapter 12 defers ACID to this chapter). The code also comes in dense blocks. Five libraries or APIs appear with no introduction: sqlite3, `.arrow().read_all()`, `con.register`, `SELECT * REPLACE`, and the PyArrow metadata API. Object storage, a core idea here, is used for the first time in the book with a one-cell definition.
Size: ~845 lines, 20 book pages (119–138), 7 code blocks plus 1 in the answers, 14 exercises, a 9-step project. Time needed stated: 12–16 hours over two to three weeks; plausible? Yes, roughly. The reading and code take about 5–6 hours and the project about 6–8. Adding the Ch 2 material, a partitioned-write cell, restore/vacuum cells and the object-storage primer (below) adds about 1–1.5 hours, so 14–17 hours is the honest figure.

## What works (keep)
- §49.2 opens with the same data in three places: CSV 14.6 MB, SQLite 16.3 MB, Parquet 1.3 MB, and the same average (196.49) from each. It is concrete, verifiable, and immediately motivating. (I rebuilt a structurally identical day: CSV 14.63 MB, reading_ts chunk 209.3 KB, units_made 62.0 KB, scrap_flag 4.1 KB all match exactly, so the outputs are real.)
- The "In plain English" warehouse analogy maps each of the eight ideas (files, partitioning, log, A/C/I/D, time travel, small files) onto one physical picture. Figure 49.2 (folder vs log) is the clearest explanation of "the log is the table" I've seen at this level.
- The Delta sequence is authentic and verified: create → read the log's four action kinds → predicate overwrite of M-07 (216,000 rows kept, version 0 → 1) → time travel → schema merge → compaction. In deltalake 1.6.x I reproduced commitInfo/protocol(minReaderVersion 3)/metaData/add, one data file after the predicate overwrite, and history `Overwrite` with a predicate.
- "In the real world: the table nobody could fix" (11 days corrected, 8 missing, 23 uncorrected = 42 ✓) is the right story in the right place. So is the "Common mistakes" table.
