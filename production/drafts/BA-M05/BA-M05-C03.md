## Purpose and evidence model

SQL lets an analyst turn a business question into a reproducible result over structured data. The language is concise, but concise syntax does not make the reasoning simple. A trustworthy query states its population, grain, time boundary, join rules, treatment of missing values, and reconciliation method. Without those decisions, valid SQL can return a misleading number.

This chapter uses a small synthetic commerce fixture: five customers, eight orders, seven order events, and six imported customer rows. The data deliberately contains an unmatched customer key, a missing amount, a missing status, a duplicate normalized email, a missing email, an unknown country code, and an invalid date string. These defects make validation visible without exposing personal or confidential data.

Examples E01-E10 were executed with Python's `sqlite3` module against SQLite 3.42.0. Their exact queries, SHA-256 hashes, runtime, and returned rows are preserved in `production/audits/BA-M05/BA-M05-C03-SQL-EXECUTION-AUDIT.json` and its Markdown companion. The tables printed here are those executed results. PostgreSQL, MySQL, and SQL Server syntax is compared against current vendor documentation, but no output is claimed for a dialect-specific snippet that was not run locally. SQLite documents that a `SELECT` returns zero or more fixed-column rows and does not modify the database [1].

### Analytical query contract

Before writing SQL, record a compact contract. It prevents reviewers from debating syntax while the business meaning remains unspecified.

| Contract field | Example for paid revenue | Control question |
|---|---|---|
| Decision | Assess February revenue performance | What action could this result change? |
| Population | Orders created from 2026-02-01 inclusive to 2026-03-01 exclusive | Which rows qualify and which do not? |
| Grain | One row per region | What does one result row represent? |
| Measure | Sum of `total_amount` for `status = 'paid'` | Are currency, refunds, tax, and nulls defined? |
| Join | Orders matched to one customer by `customer_id` | Can missing or duplicate keys change the population? |
| Validation | Reconcile source paid value to joined paid value | What independent total detects dropped rows? |

The examples are read-only after fixture creation. On a shared or production system, use a read replica or governed analytical workspace, restrict selected columns, avoid unrestricted extracts, and inspect the query plan before scanning a large table. A transaction or `SELECT` statement is not automatically harmless: it can consume substantial CPU, memory, I/O, or expose sensitive data.

## BA-05-C03-T01 - SELECT

### From a question to a result relation

`SELECT` describes a result. The select list chooses expressions and names output columns; `FROM` identifies inputs; later clauses restrict, group, and order the rows. Although SQL is written beginning with `SELECT`, analysts should reason from the population outward: source and joins, row filtering, grouping, group filtering, projection, duplicate removal, ordering, and row limiting. This conceptual order explains why an alias created in the select list is often unavailable to `WHERE`, and why a window value usually must be filtered in an outer query.

A result has a grain. `SELECT order_id, order_date` has one row per qualifying order only if `order_id` is unique in the input after joins. `SELECT region, SUM(total_amount) GROUP BY region` has one row per distinct region expression. State that grain in ordinary language before execution. If the returned columns cannot identify or describe the promised grain, the query contract and SQL disagree.

Avoid `SELECT *` in durable analysis. A schema change can silently add large or sensitive columns, alter downstream positional mappings, or make a review ambiguous. Name the required columns and give calculated expressions stable aliases. Aliases belong to the interface of an analytical dataset; `booked_amount` communicates more than a driver-generated label such as `total_amount` when the business meaning truly is booked amount. Do not rename a measure more confidently than its definition permits.

Ordering is also part of the interface. A table has no inherent display order. A query without `ORDER BY` may appear stable during testing and change after an index, execution-plan, parallelism, or engine change. When using `LIMIT`, `TOP`, or `FETCH`, provide a deterministic order with a unique tie-breaker. PostgreSQL's current `SELECT` reference explicitly treats `ORDER BY`, `LIMIT`, `OFFSET`, and `FETCH` as distinct clauses [2].

### Worked example E01 - explicit projection

Runtime: SQLite 3.42.0. Input grain: one row per order. Join: none. Null handling: preserve null amounts. Date logic: none. Safety: four columns are not extracted; only three named columns and four ordered rows are returned.

```sql
SELECT order_id,
       order_date,
       total_amount AS booked_amount
FROM orders
ORDER BY order_date, order_id
LIMIT 4;
```

Executed result:

| order_id | order_date | booked_amount |
|---|---|---|
| 101 | 2026-01-03 | 120 |
| 102 | 2026-01-12 | 40 |
| 103 | 2026-01-15 | 200 |
| 104 | 2026-02-02 | NULL |

The tie-breaker `order_id` makes the choice deterministic when two orders share a date. The `NULL` remains visible instead of being converted to zero; unknown amount and zero amount are different business facts. Validate the result by checking that all returned identifiers exist in `orders`, the row count is four, and the dates are nondecreasing.

### Failure analysis

A frequent failure is to attach meaning to a column label that the source does not support. If `total_amount` excludes refunds or includes tax inconsistently, aliasing it `revenue` does not repair the definition. Another failure is deduplicating with `DISTINCT` to hide join multiplication. `DISTINCT` changes the result population and may collapse legitimately repeated rows. Find the incorrect grain or join instead.

Column expressions can also fail through implicit conversion. Comparing numeric text with a number, or combining timestamps in different zones, produces engine-specific behavior and sometimes an error. Prefer controlled data types upstream and explicit conversions where unavoidable. Treat conversion failures as data-quality evidence rather than replacing every bad value with a default.

Advanced practice is to make the result contract testable: assert column names, data types, row-grain uniqueness, allowable nullability, and a reconciliation total. SQL then becomes one part of a governed analytical interface rather than an isolated script.

## BA-05-C03-T02 - filters

### Predicates define the population

`WHERE` retains rows for which its predicate evaluates to true. SQL uses three-valued logic: a predicate may be true, false, or unknown. Comparisons with `NULL`, including `status = NULL` and `status <> 'paid'`, do not produce ordinary true or false for a missing status. Test missingness with `IS NULL` or `IS NOT NULL`, and decide whether unknown values belong in the population.

Parentheses make mixed `AND` and `OR` logic reviewable. `AND` normally binds more tightly than `OR`, but relying on precedence makes changes risky. Write `region = 'North' AND (status = 'paid' OR status IS NULL)` if that is the intended rule. Then test a row from every logical branch: paid North, null-status North, nonpaid North, and paid non-North.

For timestamp periods, prefer a half-open interval: start inclusive and next-period start exclusive. `event_at >= '2026-02-01' AND event_at < '2026-03-01'` handles every time on the last day without guessing timestamp precision. `BETWEEN` is inclusive at both ends, which is useful for some numeric bounds but hazardous if an analyst writes an end date at midnight. Define the reporting timezone before translating a business day into timestamp boundaries.

Text filters require an explicit case and whitespace policy. A user-entered status might contain `Paid`, `paid`, or trailing spaces. Normalizing in every query can be expensive and may prevent index use; governed normalization at ingestion is usually safer. Pattern matching also differs among dialects and collations. Treat case-insensitive behavior as a dialect and data-model choice, not a universal property of SQL.

### Worked example E02 - period and missing status

The question is: which February orders are paid or have an unresolved status? Runtime: SQLite 3.42.0. Grain: one row per order. Join: none. Null handling: include null status explicitly and preserve null amount. Date logic: ISO dates stored in a consistently padded text format, with a half-open month. In a production model, use a real `DATE` or timestamp type.

```sql
SELECT order_id, status, total_amount
FROM orders
WHERE order_date >= '2026-02-01'
  AND order_date <  '2026-03-01'
  AND (status = 'paid' OR status IS NULL)
ORDER BY order_id;
```

Executed result:

| order_id | status | total_amount |
|---|---|---|
| 105 | paid | 80 |
| 106 | paid | 60 |
| 107 | NULL | 150 |

Order 104 is in February but excluded because it is pending. Order 107 is included because the contract explicitly asks for unresolved status. Its inclusion should not be mistaken for paid revenue. This distinction shows why a row-level investigation query and a financial measure query require different predicates.

### Boundary and negation failures

`NOT IN` is dangerous when its list or subquery contains `NULL`: unknown comparisons can prevent every row from qualifying. `NOT EXISTS` often expresses anti-matching more safely, provided the correlation predicate is correct. Likewise, `status <> 'refunded'` excludes null statuses because unknown is not true. If the intended population is all orders not known to be refunded, write and document `(status <> 'refunded' OR status IS NULL)`.

Validate filters with counts before and after each major predicate, minimum and maximum dates, null counts, and a small sample of excluded rows. Never validate only the rows that survived. For a material decision, ask the business owner to approve the population statement separately from the SQL implementation.

## BA-05-C03-T03 - joins

### Join type is a population decision

A join combines rows using a predicate. An inner join retains matching combinations. A left join retains every row from the left input and supplies nulls for unmatched right-side columns. Right and full outer joins express related preservation rules, though SQLite does not share the same historical support profile as enterprise engines. Choose a join based on the population the question must preserve, not habit.

Cardinality is the central control. If each order has one customer, the expected relationship is many orders to one customer. A duplicate `customer_id` in an ungoverned customer snapshot multiplies order rows and inflates revenue. Conversely, an inner join drops an order whose customer key is absent. Both queries can execute without error. Before joining, profile uniqueness on the expected one-side, null keys on both sides, and unmatched keys in each required direction.

Place relationship predicates in `ON`. Be careful with filters on the nullable side of an outer join. `LEFT JOIN orders o ... WHERE o.status = 'paid'` removes customers with no matching paid order and behaves like an inner join for that condition. If the population must include all customers, put `o.status = 'paid'` in the `ON` clause or use conditional aggregation, depending on the exact question.

Composite business keys need every component. Joining a monthly target by region alone when the actual key is region plus month creates many-to-many multiplication. A surrogate key reduces syntax but does not remove the duty to validate the relationship. Temporal joins add another issue: the correct dimension row may be the version effective at the event time, not the dimension's current row.

### Worked example E03 - customers including zero orders

The required population is all five customers, including those without orders. Runtime: SQLite 3.42.0. Result grain: one row per customer. The left input owns the population. `COUNT(o.order_id)` counts only matched non-null order identifiers; `COUNT(*)` would return one for Elm Services because the preserved left row still exists.

```sql
SELECT c.customer_id,
       c.customer_name,
       COUNT(o.order_id) AS order_count
FROM customers AS c
LEFT JOIN orders AS o
  ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.customer_name
ORDER BY c.customer_id;
```

Executed result:

| customer_id | customer_name | order_count |
|---|---|---|
| 1 | Aster Stores | 2 |
| 2 | Beacon Labs | 2 |
| 3 | Cedar Works | 2 |
| 4 | Delta Retail | 1 |
| 5 | Elm Services | 0 |

The result totals seven matched orders, not the eight rows in `orders`; order 106 points to absent customer 99. That difference is not a rounding issue. It is an unmatched-key exception and must be reconciled before using the joined data for revenue.

### Join control table

| Check | Query idea | Failure revealed |
|---|---|---|
| One-side uniqueness | Group customer key and retain count greater than one | Fan-out and inflated measures |
| Left unmatched | Left join and retain null right key | Dropped facts if an inner join is used |
| Right unmatched | Reverse anti-join where relevant | Unused or mis-keyed dimension records |
| Row reconciliation | Compare counts before and after join | Unexpected multiplication or loss |
| Measure reconciliation | Compare source and joined sums | Silent monetary distortion |

The analyst should record expected and actual relationship cardinality. If a many-to-many join is legitimate, state the allocation rule that prevents double counting. If there is no defensible rule, stop the analysis rather than masking the multiplication with `DISTINCT`.

## BA-05-C03-T04 - aggregation

### Measures, dimensions, and grain

Aggregation converts a set of detail rows into measures such as `COUNT`, `SUM`, `MIN`, `MAX`, and `AVG`. `GROUP BY` defines the dimensions that partition those rows. The selected nonaggregate expressions must align with the grouped grain, subject to dialect rules. SQLite documents permissive behavior for bare columns in aggregate queries [1], while stricter engines or modes reject ambiguous selections. Portable analytical SQL names every dimension in the grouping rule.

Null handling differs by function. `COUNT(*)` counts rows. `COUNT(column)` counts non-null values. `SUM` and `AVG` ignore null inputs, and an all-null group may return null rather than zero. `COALESCE` can map a null to a reporting bucket or zero, but only after the business meaning is decided. Unknown region is not necessarily the same as an intentionally defined region called Other.

Distinctness belongs to the measure definition. `COUNT(DISTINCT customer_id)` counts customers represented in qualifying facts, not all registered customers. A distinct count across distributed or approximate systems may have special performance or accuracy characteristics. Record whether the metric is exact and which entity key is used.

Never average averages unless the groups have equal and relevant denominators. To combine conversion rates, sum converted events and eligible events, then divide, with a stated zero-denominator rule. Similar care applies to currency: sum only amounts in a common currency and consistent accounting state.

### Worked example E04 - paid revenue by region

Runtime: SQLite 3.42.0. Source grain: one row per order. Result grain: one row per normalized customer region. Join: inner many-to-one, which intentionally excludes the orphan order. Null region is labeled Unknown. Paid orders with null amount would increase `paid_orders` but contribute nothing to `SUM`; therefore the measure needs a separate null-amount control.

```sql
SELECT COALESCE(c.region, 'Unknown') AS region,
       COUNT(*) AS paid_orders,
       ROUND(SUM(o.total_amount), 2) AS paid_revenue
FROM orders AS o
JOIN customers AS c
  ON c.customer_id = o.customer_id
WHERE o.status = 'paid'
GROUP BY COALESCE(c.region, 'Unknown')
ORDER BY paid_revenue DESC, region;
```

Executed result:

| region | paid_orders | paid_revenue |
|---|---|---|
| North | 2 | 200 |
| South | 1 | 200 |
| Unknown | 1 | 90 |

North and South tie at 200, so `region` is a deterministic secondary ordering expression. The three displayed groups sum to 490, while the paid-order source sums to 550. The missing 60 is the orphan order, not a calculation error. A report that presents 490 without that reconciliation understates the source population.

### HAVING and denominator failures

`WHERE` filters rows before grouping; `HAVING` filters groups after aggregation. A condition such as `HAVING SUM(total_amount) >= 100` is a group rule. Moving it to `WHERE` is either invalid or changes meaning. PostgreSQL describes a query with `HAVING` as grouped even without an explicit `GROUP BY` [2].

Common aggregation defects include joining facts before aggregation at an incompatible grain, counting nullable columns unintentionally, dividing integers under a dialect's numeric rules, and excluding zero-activity entities. Validate with a grand total, group-count expectations, null counts for every measure input, and a detail drill-through for the largest and smallest groups.

## BA-05-C03-T05 - CTEs

### Named stages, not stored results

A common table expression is a named result available within one statement. It can make a multi-stage analysis legible: establish the eligible population, aggregate it, then enrich it. MySQL defines a CTE as a named temporary result set within a single statement and permits multiple comma-separated CTEs in one `WITH` clause [3]. SQL Server similarly describes a CTE as a temporary named result within the execution scope of a statement [4]. The word temporary describes scope, not guaranteed physical storage.

Do not assume a CTE is materialized, cached, or faster. Optimizers can inline, merge, or materialize expressions depending on dialect, version, query shape, and hints. If performance matters, inspect the actual execution plan and measured resource use. A CTE is primarily a decomposition and naming tool unless the engine documentation and plan prove a physical behavior.

Each stage should preserve an explainable grain. Name CTEs after the data they contain, such as `paid_orders`, rather than steps such as `cte1`. List columns explicitly when names would otherwise be ambiguous. Avoid long chains that merely move every clause into a new box; decomposition should expose business rules and validation points.

Recursive CTEs support hierarchies and sequences in capable systems. They require an anchor member, a recursive member, a termination condition, and controls against cycles or excessive depth. Because recursion is outside this chapter's worked fixture, it is acknowledged but not assigned an expected output here.

### Worked example E05 - staged customer revenue

Runtime: SQLite 3.42.0. The first CTE has one row per paid order. The second has one row per customer key. The final inner join adds the customer name and drops orphan key 99. Null handling follows `SUM`; paid orders with unknown amounts need a separate exception query.

```sql
WITH paid_orders AS (
  SELECT customer_id, total_amount
  FROM orders
  WHERE status = 'paid'
),
customer_revenue AS (
  SELECT customer_id, SUM(total_amount) AS revenue
  FROM paid_orders
  GROUP BY customer_id
)
SELECT c.customer_name, cr.revenue
FROM customer_revenue AS cr
JOIN customers AS c
  ON c.customer_id = cr.customer_id
ORDER BY cr.revenue DESC, c.customer_name;
```

Executed result:

| customer_name | revenue |
|---|---|
| Beacon Labs | 200 |
| Aster Stores | 120 |
| Delta Retail | 90 |
| Cedar Works | 80 |

The four customer amounts total 490. The CTE improves traceability because a reviewer can run `SELECT * FROM paid_orders` or `SELECT * FROM customer_revenue` during diagnosis, but the production statement still needs end-to-end reconciliation.

### Scope and maintenance failures

A CTE exists only for its statement. Referencing it from a later statement fails. A forward reference or nested `WITH` may be accepted differently by dialects; MySQL, for example, restricts same-level `WITH` usage and CTE name resolution [3]. SQL Server often requires the preceding statement to end with a semicolon before `WITH`. Those are portability concerns, not reasons to abandon clear staging.

A more serious analytical failure is reusing a CTE name whose grain changed during maintenance. Document the grain in a short comment and review every downstream join after changing it. Where repeated business logic must stay consistent across many analyses, a governed view or modeled table may be more appropriate than copying a CTE.

## BA-05-C03-T06 - windows

### Calculations that retain detail rows

A window function calculates across rows related to the current row while retaining a result for each detail row. This contrasts with ordinary aggregation, which collapses a group into one row. PostgreSQL requires an `OVER` clause for a function to act as a window function [5]. The window definition can partition rows, order them, and specify a frame.

`PARTITION BY` restarts the calculation for each group. Window `ORDER BY` defines sequence inside the calculation; it does not guarantee final display order. The outer query still needs its own `ORDER BY`. Ranking functions also need deterministic tie-breakers if consumers expect stable positions. `ROW_NUMBER` assigns unique sequence numbers, while `RANK` and `DENSE_RANK` represent ties differently.

Frames are essential for running and moving calculations. With an ordered aggregate window, an engine's default frame can group peers in ways that surprise an analyst. Write `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` for an explicit row-by-row running total. MySQL supports `ROWS` and `RANGE` but documents restrictions on features such as `GROUPS` and `EXCLUDE` [6].

Window functions are generally evaluated after `WHERE`, grouping, and `HAVING`, and are allowed in the select list or ordering stage in major dialects. PostgreSQL recommends an outer subquery when filtering on a calculated window value [7]. Some platforms offer `QUALIFY`, but it is not portable across the four dialects discussed here.

### Worked example E06 - rank and running amount

Runtime: SQLite 3.42.0. Input and output grain: one row per qualifying order. Partition: customer. Rank order: amount descending with order identifier tie-breaker. Running-total order: date and identifier. Null amounts are excluded explicitly. The two window orderings answer different questions and should not be conflated.

```sql
SELECT customer_id,
       order_id,
       total_amount,
       ROW_NUMBER() OVER (
         PARTITION BY customer_id
         ORDER BY total_amount DESC, order_id
       ) AS amount_rank,
       SUM(total_amount) OVER (
         PARTITION BY customer_id
         ORDER BY order_date, order_id
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_amount
FROM orders
WHERE total_amount IS NOT NULL
  AND customer_id IN (1, 2, 3)
ORDER BY customer_id, order_date, order_id;
```

Executed result:

| customer_id | order_id | total_amount | amount_rank | running_amount |
|---|---|---|---|---|
| 1 | 101 | 120 | 1 | 120 |
| 1 | 102 | 40 | 2 | 160 |
| 2 | 103 | 200 | 1 | 200 |
| 3 | 105 | 80 | 2 | 80 |
| 3 | 107 | 150 | 1 | 230 |

For customer 3, order 107 has rank 1 by amount but appears after order 105 in time, so its running amount is 230. That is correct because rank and cumulative sequence use separate order definitions.

### Window failure analysis

Missing tie-breakers cause nondeterministic ranks. A default frame may include peer rows and make a running total jump. Filtering rows before a window calculation changes the partition; filtering after it selects from the computed sequence. Large partitions and sorts may spill to disk. Validate the number of input and output rows, the first and last running values in each partition, tie behavior, and agreement between final running totals and grouped totals.

Do not use a window calculation merely because it looks sophisticated. If the required result is one row per customer, an ordinary `GROUP BY` is clearer. Windows are appropriate when the detail rows and a relationship-to-group measure must coexist.

## BA-05-C03-T07 - data-quality queries

### SQL as a diagnostic instrument

Data-quality queries measure violations of an agreed rule; they do not define quality in the abstract. A useful check names the field, population, rule, severity, owner, threshold, and response. Dimensions commonly include completeness, uniqueness, validity, consistency, referential integrity, and timeliness. Accuracy usually requires comparison with an authoritative external fact and cannot be proven from one table alone.

Return both a count and inspectable exceptions. A dashboard that reports one duplicate without identifying the normalized key is difficult to repair. Conversely, exporting every personal record may violate least-privilege rules. Use synthetic examples, restrict production access, and expose only the identifiers required for remediation.

Normalization must match the governed business key. Lowercasing and trimming email is useful for this fixture but is not a universal identity rule. Internationalized addresses, provider-specific behavior, shared mailboxes, and recycled addresses complicate identity. A duplicate query should say "duplicate under this normalization," not "same person."

### Worked example E07 - duplicate normalized keys

Runtime: SQLite 3.42.0. Grain: one row per duplicated normalized email value. Null emails are excluded from the uniqueness comparison and should be assessed separately for completeness.

```sql
SELECT LOWER(TRIM(email)) AS normalized_email,
       COUNT(*) AS row_count
FROM customer_import
WHERE email IS NOT NULL
GROUP BY LOWER(TRIM(email))
HAVING COUNT(*) > 1
ORDER BY normalized_email;
```

Executed result:

| normalized_email | row_count |
|---|---|
| ana@example.test | 2 |

The result proves two rows share one normalized string. It does not prove which row should survive. Remediation needs a source identifier, survivorship rule, and audit trail.

### Worked example E08 - referential integrity exception

Runtime: SQLite 3.42.0. Grain: one row per orphan order. The left join preserves every order, then the null customer key identifies unmatched rows.

```sql
SELECT o.order_id, o.customer_id
FROM orders AS o
LEFT JOIN customers AS c
  ON c.customer_id = o.customer_id
WHERE c.customer_id IS NULL
ORDER BY o.order_id;
```

Executed result:

| order_id | customer_id |
|---|---|
| 106 | 99 |

Possible causes include delayed dimension loading, an incorrect source key, deleted reference data, or a broken transformation. The query detects the symptom. Root-cause investigation determines the response.

### Worked example E09 - completeness and domain validity

Runtime: SQLite 3.42.0. Grain: one summary row for the six imported records. `CASE` converts each violation into 1 so it can be summed. The allowed country list is an example rule owned by the fixture, not a complete real-world list.

```sql
SELECT
  SUM(CASE WHEN email IS NULL OR TRIM(email) = '' THEN 1 ELSE 0 END) AS missing_email,
  SUM(CASE WHEN country_code NOT IN ('IN','US','GB') THEN 1 ELSE 0 END) AS invalid_country,
  COUNT(*) AS total_rows
FROM customer_import;
```

Executed result:

| missing_email | invalid_country | total_rows |
|---|---|---|
| 1 | 1 | 6 |

The invalid text date is not counted by this query, demonstrating why a quality score is only as complete as its rule inventory. In SQLite, flexible typing can admit values a stricter engine rejects. Validate dates with an ingestion contract or an engine-appropriate safe conversion, and retain the raw value for diagnosis.

### Worked example E10 - monetary reconciliation

Runtime: SQLite 3.42.0. Each CTE returns one summary row. The difference isolates paid value removed by the customer join.

```sql
WITH source_total AS (
  SELECT SUM(total_amount) AS amount
  FROM orders
  WHERE status = 'paid'
),
matched_total AS (
  SELECT SUM(o.total_amount) AS amount
  FROM orders AS o
  JOIN customers AS c ON c.customer_id = o.customer_id
  WHERE o.status = 'paid'
)
SELECT source_total.amount AS source_paid,
       matched_total.amount AS matched_paid,
       source_total.amount - matched_total.amount AS unmatched_paid
FROM source_total CROSS JOIN matched_total;
```

Executed result:

| source_paid | matched_paid | unmatched_paid |
|---|---|---|
| 550 | 490 | 60 |

Reconciliation converts a vague warning about missing keys into a quantified business impact. The next decision is whether to repair order 106, report it in an Unknown customer bucket, or exclude it under an approved policy. SQL should expose that choice rather than silently make it.

## BA-05-C03-T08 - dialects

### Shared language, different contracts

SQL implementations share core relational ideas but differ in syntax, data types, functions, null ordering, identifier rules, collation, date arithmetic, pagination, safe conversion, and optimizer behavior. A query is reproducible only when its dialect and supported version are named. "Runs in SQL" is not an adequate runtime statement.

The current references used here are PostgreSQL 18 documentation, MySQL 8.4 documentation, SQL Server Transact-SQL documentation, and SQLite's maintained language reference [1]-[8]. These versions are research anchors, not promises about the learner's environment. Check the deployed engine and compatibility mode at authoring and execution time.

| Need | PostgreSQL | MySQL 8.4 | SQL Server | SQLite |
|---|---|---|---|---|
| Limit ordered rows | `LIMIT 10` or standard `FETCH` | `LIMIT 10` | `TOP (10)` or `OFFSET ... FETCH` | `LIMIT 10` |
| Null replacement | `COALESCE(x, 0)` | `COALESCE(x, 0)` | `COALESCE(x, 0)` or `ISNULL(x, 0)` | `COALESCE(x, 0)` |
| Concatenate text | `a || b` | `CONCAT(a,b)` | `CONCAT(a,b)` or `a + b` with null caveats | `a || b` |
| Date plus one day | `d + INTERVAL '1 day'` | `DATE_ADD(d, INTERVAL 1 DAY)` | `DATEADD(day, 1, d)` | `date(d, '+1 day')` |
| Quote identifier | `"name"` | backticks by default | brackets or quoted identifiers | `"name"` |

The table is a portability map, not executed-output evidence. Each expression must be tested on the target engine with the real data type. Even apparently portable `COALESCE` can produce different resulting types because engines apply different type-precedence rules.

### Pagination comparison without claimed output

PostgreSQL, MySQL, and SQLite commonly express a first page as:

```sql
SELECT order_id, order_date
FROM orders
ORDER BY order_date, order_id
LIMIT 10;
```

SQL Server commonly uses:

```sql
SELECT TOP (10) order_id, order_date
FROM orders
ORDER BY order_date, order_id;
```

These snippets have no expected-result table because only the SQLite form was executed in E01. The relevant lesson is that limiting without a deterministic `ORDER BY` makes page membership unstable. Offset pagination can also skip or repeat rows when concurrent changes occur; keyset pagination using the last ordered key is often more stable for large, changing datasets.

### CTE and window differences

All four engines support ordinary CTEs and common window functions, but edge features differ. MySQL documents unsupported window features including `GROUPS` frames and `EXCLUDE`, while PostgreSQL documents a broader window-function model [5][6]. SQL Server's CTE rules include statement-boundary and clause restrictions [4]. SQLite explicitly documents deviations and permissive join syntax, which is a reason to test portability rather than infer it [1].

Default null sorting differs. Instead of depending on defaults, encode intent where portable. One technique is `ORDER BY CASE WHEN value IS NULL THEN 1 ELSE 0 END, value`, then validate on the target engine. Case sensitivity may depend on database, column collation, operator, and configuration. Never claim a text filter is case-sensitive or insensitive without checking that environment.

### Migration failure analysis

Mechanical search-and-replace is insufficient for dialect migration. A query can parse and still change results through integer division, timestamp conversion, week numbering, collation, null order, or bare-column aggregation. Build a golden fixture with edge cases, run both versions, compare typed results, and review the plan. Where engines are unavailable, mark the query unverified rather than inventing an expected result.

Provider extensions can create lock-in but also improve safety or clarity. The right decision is explicit: use portable core syntax where it meets the need; use an extension when its value is material; isolate and document it; and test it in the supported version. Dialect awareness is not memorizing four vocabularies. It is maintaining an execution contract.

## Advanced analyst practices across the eight topics

### Designing SELECT outputs as governed interfaces

A one-off query often becomes a recurring extract, dashboard source, or decision control. Treat its selected columns as an interface from the beginning. Give each output field a business definition, data type, nullability expectation, unit, and example. Separate identifying dimensions from measures, and make derived measures traceable to their source expressions. If a label says `net_revenue`, a reviewer should be able to locate the treatment of discounts, refunds, tax, shipping, currency, and recognition date. A shorter query is not better when it hides those decisions.

Stable interfaces also require change control. Adding a selected column is usually compatible for name-based consumers but can break position-based imports. Renaming or changing a type is breaking. Removing a column is plainly breaking. A view or modeled table can provide a durable contract, but only when ownership and deployment practices exist. For an ad hoc file, version the query beside the output and record the extraction time, source snapshot, row count, and control total.

Expression design affects both meaning and performance. A calculation repeated in several selected fields can drift when one copy changes. A well-named CTE can compute it once, while a governed semantic layer may be appropriate for organization-wide measures. However, abstraction must not make the logic impossible to inspect. The reviewer should be able to move from displayed field to source evidence without guessing.

Consider privacy at projection time. Selecting an email address "just in case" increases disclosure risk even if the final chart does not display it. Use non-sensitive identifiers for joins and return only fields needed by the decision. Aggregation does not automatically anonymize a result: a group with one person may still reveal individual information. Apply minimum-group or suppression rules when policy requires them, and do not invent thresholds without the responsible privacy owner.

For durable results, add deterministic identifiers and ordering only where the consumer needs them. Ordering a large intermediate dataset may waste resources because a later operation can discard the sequence. The final consumer-facing extraction needs stable order; an internal relational stage generally needs a declared grain and key. This distinction keeps both meaning and execution efficient.

### Building filter test matrices

A filter is easiest to review as a truth table. List representative rows around every boundary and state whether each must be included. For a monthly period, include a timestamp immediately before the start, exactly at the start, within the month, immediately before the next month, and exactly at the next-month boundary. Add a null timestamp and a timestamp expressed in a different zone if those states can occur. This catches more errors than reading the predicate repeatedly.

Business labels such as active, churned, eligible, and overdue often compress several conditions. Decompose the label before translating it. An active customer might require a nonclosed account, at least one paid transaction in 90 days, and no fraud hold. Those conditions may use different tables and clocks. Document whether "today" means execution time, report effective date, or source-system business date. A reproducible report accepts an explicit as-of value instead of embedding a moving current-date function without record.

Parameterization separates values from SQL structure and protects against injection when input originates outside the analyst's control. Parameters do not make an incorrect filter correct, but they prevent a value such as a quote from being treated as executable syntax by a properly used driver. Allow-list any dynamic identifiers, sort directions, or optional clauses that cannot be bound as ordinary values. Never build unrestricted SQL by concatenating a user-supplied string.

Push filters into the database when this preserves meaning, because transferring an entire table to a spreadsheet or notebook is slower and expands the sensitive-data footprint. Yet predicate placement around outer joins changes results, as discussed earlier. Performance advice must remain subordinate to semantics. Compare explain plans and execution metrics only after establishing a correct reference result.

Finally, retain excluded-population diagnostics. A report can show 100 eligible cases while a companion control states that 12 were excluded for missing consent, 4 for an invalid date, and 3 for unknown status. That control makes changes explainable and reveals when a source-system defect, rather than business performance, moves the headline number.

### Proving join cardinality before trusting measures

Join validation begins with hypotheses. Write "orders many-to-one customers on non-null customer_id" before execution. Test uniqueness of the customer key, null keys in orders, unmatched order keys, and counts at each stage. If the customer table is a history table, uniqueness may be by customer plus effective interval rather than customer alone. The hypothesized relationship must match the modeled time semantics.

For a left join, reconcile at least three quantities: left input rows, matched left entities, and unmatched left entities. If right-side duplicates are possible, also report result rows and the maximum matches per left key. A result row count equal to the left input is reassuring only for an expected one-to-one or many-to-one relationship; it does not prove that each match is the correct match.

Measure reconciliation catches distortions row counts miss. Two errors can cancel: duplicated positive amounts and dropped positive amounts may leave the row count or total apparently unchanged. Compare multiple controls, such as count, sum, distinct keys, minimum date, maximum date, and null counts. For financial work, reconcile by meaningful partitions such as day, currency, or source system, not just one global total.

Many-to-many relationships sometimes represent reality, such as orders associated with multiple campaigns. The raw join still duplicates an order measure. Decide whether credit is full, fractional, first-touch, last-touch, or excluded from additive reporting. Store or calculate an allocation weight and prove that weights sum to the intended amount for every order. Without an allocation rule, the relationship supports association analysis but not a simple revenue sum.

Temporal joins deserve special caution. A customer can change region after an order. Joining every historical order to the current customer row rewrites history. A point-in-time join chooses the dimension version whose effective interval contains the order timestamp. Intervals must not overlap for the same entity, and boundary conventions should be half-open. Test orders at the exact effective transition.

When a join fails, do not immediately coalesce missing identifiers into one generic key. An Unknown member can keep facts visible in reporting, but it should be governed and accompanied by exception counts and remediation ownership. Otherwise a growing Unknown bucket conceals upstream failure.

### Designing additive and nonadditive aggregations

Measures behave differently across dimensions. Transaction amount is usually additive across orders and time when currency and accounting state are aligned. Inventory balance is additive across products but not across dates; summing daily snapshots exaggerates inventory. Ratios, percentages, medians, and distinct counts are generally nonadditive. A result can be syntactically grouped and still be mathematically invalid.

Define a measure with numerator, denominator, eligibility, time basis, unit, and null rule. For conversion rate, decide whether a customer, session, lead, or opportunity is the counting entity. Then calculate distinct or deduplicated numerator and denominator at that grain. Ensure the numerator is a subset of the denominator unless the metric intentionally says otherwise. State what occurs at denominator zero: null, suppressed, zero, or not applicable.

Conditional aggregation can compute related measures from one controlled population, but each condition must be reviewed. Counts of paid and refunded orders should reconcile with total orders only if statuses are mutually exclusive, collectively exhaustive, and missing status is included as a category. Produce an Unknown measure rather than letting null states disappear.

Aggregation after a join inherits the join's cardinality. A safe pattern is to aggregate each fact source to the intended join grain before combining measures. For example, aggregate orders and support tickets separately to one row per customer, then join those summaries. Joining detailed orders directly to detailed tickets creates an order-ticket combination and inflates both counts.

Rounding belongs near presentation unless policy defines otherwise. Rounding each transaction and then summing can differ from summing full precision and rounding the final value. Floating binary types can also introduce display artifacts. Use appropriate exact numeric types for currency according to the target engine, preserve currency codes, and document scale. The SQLite fixture is instructional; its dynamic typing is not a recommendation for a production financial schema.

Advanced validation includes invariant checks. Regional values should sum to the reconciled total after approved unmatched treatment. Subcategory values should not exceed their parent population. An average should lie between the minimum and maximum for a nonempty group. These constraints do not prove the business rule is correct, but they cheaply detect entire classes of errors.

### Using CTEs for inspectable analytical stages

An effective CTE chain mirrors the reasoning record. A first stage selects the source population, a second applies governed classifications, a third aggregates to the decision grain, and a final stage formats the output. Each stage has a short name and one purpose. During review, temporarily select from each stage and record counts and control totals. The final query stays one executable statement, while its logic remains inspectable.

CTEs can also centralize parameters. A one-row parameter CTE can carry an explicit start date, end date, and reporting currency into later stages. Whether that exact syntax is portable depends on how typed literals are expressed, so test it in the target dialect. The design benefit is that every branch uses the same approved period rather than repeating subtly different literals.

Do not confuse readable decomposition with correctness. A beautifully named stage can still filter the wrong population. Pair names with assertions in the surrounding validation process. If `eligible_orders` unexpectedly has zero rows or more rows than `orders`, fail the pipeline or flag the output. A manual reviewer should not have to notice a suspicious blank chart.

Repeated references can have performance implications. An engine may inline a CTE and repeat work, or materialize it and consume memory or temporary storage. The same syntax can behave differently after an upgrade. Use the target engine's plan tools, realistic data volume, and representative parameters. A local fixture validates logic and expected rows, not production performance.

For recursive CTEs, maintain depth, path, and cycle controls. Organizational hierarchies and bill-of-materials structures can contain accidental loops. A recursion that assumes a tree may run until an engine limit, duplicate paths, or overcount descendants. If the business needs hierarchy analysis, define whether multiple parents are allowed and whether results describe nodes, edges, or paths.

When a CTE grows into shared business logic, promote it deliberately. A governed view, transformation model, or semantic measure can provide reuse, testing, lineage, and ownership. Copying a long CTE among reports produces silent forks. Promotion is not automatic: security filters, refresh behavior, compatibility, and change management must be designed.

### Selecting window definitions that match the decision

Every window calculation has four decisions: function, partition, order, and frame. `ROW_NUMBER` with no partition ranks the entire filtered population. Adding a region partition answers a different question. An order by amount ranks value; an order by event time creates sequence. A frame determines which neighboring rows contribute to aggregate-like functions. Write all four in ordinary language before relying on the syntax.

Ties are business decisions. If two orders have the same amount, `ROW_NUMBER` forces an arbitrary sequence unless another stable column breaks the tie. `RANK` gives both the same position and leaves a gap; `DENSE_RANK` leaves no gap. For a top-three award, those alternatives can select different numbers of recipients. The owner must choose the rule, and the query should make it visible.

Running totals require a complete event order. If timestamps have only date precision, multiple events may be peers. Adding an identifier as tie-breaker makes execution deterministic but may invent a business sequence that did not exist at capture time. In that case, a daily cumulative total may be more honest than a transaction-by-transaction progression. Precision in SQL cannot recover missing source evidence.

Moving averages need a frame that matches the calendar question. Seven preceding rows is not always seven days when dates are missing or multiple rows occur per day. Aggregate to one row per date first, join to a calendar if zero-activity dates matter, and then define the window. `ROWS`, `RANGE`, and engine-specific interval frames are not interchangeable.

Filtering deserves two explicit populations: the input to the window and the output after the calculation. To find the top order within each customer, calculate the rank over all eligible customer orders and filter rank in an outer query. Filtering to large orders first and then ranking answers top among already-large orders. PostgreSQL and MySQL place window evaluation after row and group filters in their documented logical model [7][8].

Validate windows using small partitions that expose ties, nulls, first rows, last rows, and frame boundaries. Compare the last running total to a separate grouped total. Confirm that the output row count matches the input when no post-window filter is applied. These controls reveal partition leaks and default-frame surprises quickly.

### Operating data-quality queries as controls

A diagnostic query becomes a control only when it is scheduled, thresholded, owned, and connected to a response. Store the run timestamp, source snapshot or batch identifier, rule version, observed count, denominator, threshold, and disposition. A green result means the defined check passed on that observed data; it does not certify unmeasured quality dimensions.

Use severity based on business impact. A missing optional marketing attribute may be informational, while an orphan financial transaction may block publication. Thresholds can be absolute, proportional, or both. A percentage alone can hide a large number in a large dataset; an absolute count alone can overreact to trivial rates. Define thresholds with the data owner and risk owner.

Trend exception rates rather than viewing one run in isolation. A stable low error rate and a sudden spike require different responses. Segment by source, ingestion batch, or business unit to localize problems, but protect small or sensitive groups. Keep rule changes visible, because a trend break may reflect a new definition rather than worse source data.

Quality queries must themselves be tested. Seed a known violation and prove the rule catches it; seed a valid edge case and prove it is not falsely rejected. The fixture in this chapter follows that pattern: duplicated normalized email, orphan key, missing email, and invalid country are intentional. The execution audit records exact returned evidence.

Repair is separate from detection. Automatic deletion of duplicates or replacement of unknown values can destroy evidence. Quarantine suspect rows, retain raw values, record transformation lineage, and apply an approved survivorship or correction rule. Re-run the diagnostic after repair and reconcile the before-and-after population.

Quality control also includes freshness. A table can be complete and valid but too old for the decision. Compare the maximum source event time with the expected service level, distinguish source delay from pipeline delay, and define timezone. Never substitute the query execution timestamp for source freshness.

### Managing dialects through tests and compatibility boundaries

Maintain a small compatibility suite for shared analytical logic. It should contain schema creation appropriate to each engine, edge-case fixtures, the dialect-specific query, expected typed rows, and comparison rules for numeric precision and timestamp representation. Run it when changing a query, driver, engine version, or compatibility setting. A static syntax matrix is helpful documentation but cannot replace execution.

Keep dialect-specific code behind a clear boundary. A repository might place shared definitions in one model and separate renderings for PostgreSQL, MySQL, and SQL Server. Name the tested engine versions in metadata. If only one dialect is actually supported, say so plainly rather than presenting superficially portable SQL.

Date and time behavior deserves dedicated tests. Check daylight-saving transitions in relevant zones, month ends, leap years, fractional seconds, and conversion between date and timestamp. "Last 30 days" differs from "current calendar month," and both differ from "previous complete local business day." Functions and interval syntax vary, but the semantic contract should remain constant.

Text behavior needs representative Unicode, accents, mixed case, trailing spaces, and nulls. Collation can change equality, ordering, and grouping. An identifier that compares equal under one collation may be distinct under another. Do not use a display label as a cross-system key without a governed normalization and collision policy.

Query plans are also dialect and version specific. Index use, CTE handling, join algorithms, statistics, and parameter sensitivity can change. Capture relevant plans for expensive recurring queries, but do not freeze a plan merely because it was once fast. Monitor runtime, scanned rows, spills, and resource consumption with production-like distributions.

Migration acceptance compares meaning, not only row count. Compare keys and typed values, reconcile totals by partitions, examine nulls, and investigate every difference. Some differences may be approved corrections, but they need a recorded decision. When the target runtime is unavailable, retain an `UNVERIFIED_ON_TARGET` state and never fabricate output to make documentation look complete.

## Integrated review checklist

A reviewer should be able to answer each item from the query and its surrounding record:

| Area | Required evidence |
|---|---|
| Business meaning | Decision, metric definition, owner, and intended consumer |
| Population | Inclusion, exclusion, time zone, and date boundaries |
| Grain | Input grain, output grain, and uniqueness check |
| Joins | Join type, keys, expected cardinality, and unmatched-row handling |
| Nulls | Null behavior for predicates, measures, grouping, and output |
| Reproducibility | Dialect, version, fixture or governed source, and deterministic order |
| Validation | Row counts, control totals, exception samples, and reconciliation |
| Safety | Least privilege, sensitive-column limits, resource controls, and review path |

The chapter's ten executed examples are evidence of behavior on one controlled fixture, not evidence that a production query is correct. Production acceptance requires approved definitions, representative tests, access controls, performance review, and reconciliation against the actual source system.
