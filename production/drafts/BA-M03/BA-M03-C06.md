## Chapter overview

Digital requirements translate business intent into governable expectations for connected, data-intensive, automated, and sometimes adaptive systems. This chapter introduces requirement concerns for APIs, reports, dashboards, automation, AI, security, privacy, and accessibility. It equips an analyst to ask precise questions and coordinate specialist decisions without pretending to replace engineering, legal, security, privacy, accessibility, or data-science expertise.

This chapter contains Phase 1 theory only. It does not contain API builds, dashboard labs, automation exercises, model training, penetration testing, or accessibility test assignments.

## Learning outcomes

The learner should be able to:

- define behavior, data, quality, error, and lifecycle requirements for digital interfaces;
- distinguish report and dashboard purposes, measures, freshness, and decision contexts;
- analyze automation boundaries, exceptions, human control, and operational recovery;
- state AI requirements around purpose, data, performance, oversight, monitoring, and harm;
- integrate security, privacy, and accessibility from the requirement level;
- recognize when specialist interpretation, testing, and authorization are mandatory.

## BA-03-C06-T01 - APIs

### Concept

An application programming interface (API) is a governed contract through which software components request or exchange capabilities and data. API requirements describe business purpose and observable obligations across a system boundary, not only endpoint syntax.

### Requirement dimensions

Define consumers and providers, capability, operations, resource or event semantics, inputs, outputs, identifiers, schemas, validation, business rules, authorization, consent, errors, idempotency, ordering, pagination, concurrency, rate limits, performance, availability, versioning, deprecation, monitoring, audit, support, and data classification.

Error behavior is part of the contract. Distinguish invalid requests, unauthorized access, forbidden action, missing resource, conflict, rate limiting, provider failure, and timeout without exposing sensitive internals. Specify retry and duplicate behavior where operations can be repeated.

### Lifecycle

An API requirement defines an interaction contract at a system boundary. It identifies consumers and providers, authorized operations, resource or message semantics, inputs, outputs, validation, errors, performance, availability, security, observability, compatibility, and ownership. HTTP and JSON are design choices unless mandated. OpenAPI can describe HTTP interfaces precisely, but a schema does not establish that its data meaning or policy is correct [2].

Compatibility rules matter. Specify idempotency for retried commands, correlation for tracing, pagination and ordering, timeout and rate behavior, and representation of partial failure. Adding an optional field may be safe for tolerant consumers; changing meaning under the same name is not. Error differences must not leak sensitive existence.

### Worked example - safe payment retry

A payment request carries an idempotency key, amount, currency, authority, and correlation ID. Repeating the same key and payload returns the original result; reusing it with different data is rejected. A timeout leaves the client able to query status rather than infer failure. Audit evidence links authorization, provider response, and ledger entry without logging prohibited payment data.

An API may have many consumers that the provider cannot change simultaneously. Compatibility, discoverability, consumer communication, migration period, and retirement evidence therefore belong in requirements. Technical teams define implementation, but business analysts preserve semantic meaning and stakeholder impact.

## BA-03-C06-T02 - Reports

### Concept

A report presents governed information for a defined audience, purpose, period, and decision or obligation. Report requirements begin with the question the information must answer, not with the layout of the existing spreadsheet.

### Information specification

Define audience, decision, measures and dimensions, business definitions, source, filters, calculations, time basis, currency and units, granularity, grouping, comparison, thresholds, exceptions, freshness, cutoff, corrections, distribution, access, export, retention, and reconciliation. State whether figures are provisional, restated, or certified.

Totals can disagree because systems use different event times, inclusion rules, or slowly changing definitions. Preserve lineage from displayed value to source and transformation. A visual mock-up helps confirm interpretation but does not replace semantic and control requirements.

### Control

A report requirement starts with decision, audience, population, definitions, grain, dimensions, measures, filters, time basis, refresh, reconciliation, access, export, retention, and owner. "Monthly sales" is incomplete until sales, month, inclusion, currency, refunds, cancellations, and late adjustments are defined. Totals reconcile to named authoritative sources with tolerances.

Presentation protects interpretation. Labels show units and zones; missing data is distinguished from zero; rounding is consistent; and accessible tables accompany charts. Exports inherit privacy and access controls. Historical reproduction may require retaining calculation versions, not only the latest formula.

### Worked example - two correct revenue numbers

Finance recognizes revenue after fulfilment, while operations measures accepted orders. Both are correct but answer different questions. The specification names measure, event date, currency conversion, treatment of returns, owner, and reconciliation. The dashboard no longer labels both simply "Revenue."

Reports may influence financial, regulatory, employment, customer, or operational decisions. Requirements should include authorization, segregation where necessary, sensitive-data handling, reproducibility, audit evidence, and a correction process.

## BA-03-C06-T03 - Dashboards

### Concept

A dashboard provides a concise, often interactive view of measures for ongoing awareness and action. Unlike a periodic report, it commonly emphasizes current state, trend, exception, and drill-down, but the distinction depends on purpose rather than technology.

### Decision-centered requirements

Identify audience, decisions, cadence, key measures, targets, thresholds, trend windows, segmentation, filters, drill paths, refresh and latency, alert logic, annotations, uncertainty, ownership, and action routes. Define every metric and show the last refresh and applicable period. A real-time display is harmful when the underlying data cannot support real-time interpretation.

Visual requirements include hierarchy, comparison, accessible color use, keyboard operation, text alternatives, readable labels, responsive behavior, and export needs. Avoid vanity metrics, overloaded screens, misleading axes, hidden exclusions, and rankings that encourage harmful behavior.

### Governance

A dashboard is a decision interface, not a collage. Requirements identify users, decisions, response actions, metric definitions, periods, latency, confidence, thresholds, drill paths, alerts, and access. A red indicator is useful only when threshold and accountable response are defined. Visual prominence follows consequence, not stakeholder rank.

Metric cards link to definitions, owners, sources, freshness, exclusions, and versions. Filters preserve denominators and disclose suppression. Accessibility includes keyboard operation, focus order, text alternatives, color-independent meaning, zoom, and tabular access under applicable WCAG criteria [5].

### Failure analysis - a misleading trend

A dashboard shows declining average wait but excludes abandoned users and combines channels. Segmenting and including abandonment shows vulnerable users wait longer. The corrected requirement defines population, percentile, abandonment, channel, delay, and escalation action.

Assign metric owners and change control. When a definition changes, manage historical comparability and annotate the break. Different audiences may need different views, but they should not receive contradictory definitions of the same measure.

## BA-03-C06-T04 - Automation

### Concept

Automation assigns repeatable work or decisions to technology under defined conditions. Requirements must specify the boundary of automation, not merely state that a process should be automated.

### Operating model

Define trigger, inputs, eligibility, rules, output, state transition, timing, exception, manual route, authorization, override, pause, retry, duplicate prevention, monitoring, audit, recovery, capacity, and ownership. Identify which steps remain human and what information people need to intervene effectively.

Automation can make a flawed rule faster and less visible. Validate the need and simplify unnecessary work before automating. Consider unusual cases, dependency outages, poor data, partial completion, handoff delay, worker impact, and accumulated queues after recovery.

### Control and value

Automation requirements describe triggers, inputs, rules, authority, outputs, exceptions, intervention, audit, monitoring, capacity, recovery, and retirement of prior work. Automating an unclear process scales ambiguity. Establish whether the task is stable, repeatable, authorized, observable, and valuable after exception effort and maintenance.

Define unattended-action boundaries. High-consequence decisions may require review, dual authorization, or reversible execution. Queues need priority, retry, duplicate, poison-message, and manual-work handling. Failure must not conceal unfinished work. Benefits balance cycle time against transferred workload and exception rate.

### Worked example - controlled invoice automation

Exact purchase-order matches post automatically; price, quantity, supplier, duplicate, tax, or account exceptions route to named queues. Every decision records inputs, rule version, outcome, and actor. A kill switch stops new posting while preserving queued work, and reconciliation proves no invoice was lost during recovery.

Measure outcome quality, not only time saved. Monitor errors, rework, exceptions, access, downstream harm, and control performance. High-impact or irreversible actions may require human authorization or a reliable appeal and reversal route.

## BA-03-C06-T05 - Artificial Intelligence

### Concept

AI requirements govern a system whose outputs may be probabilistic, data-dependent, adaptive, or difficult to explain. They must connect an authorized purpose to measurable performance, human responsibility, operating limits, monitoring, and remedies.

### Requirement frame

Define intended use, affected people, prohibited uses, decision role, input and training-data requirements, provenance, representativeness, performance measures, subgroup analysis, confidence or uncertainty, explainability need, human oversight, contestability, fallback, security, privacy, documentation, change control, monitoring, drift, incident response, and retirement.

Accuracy alone is inadequate. Choose measures that reflect the decision and consequences of different errors. Establish thresholds by context and affected group, and document test conditions. A model can meet an average target while harming a smaller population. Human review is not a control unless reviewers have time, authority, information, competence, and a realistic ability to disagree.

### Lifecycle and governance

AI requirements begin with the decision and consequence, not a model name. Specify intended and prohibited use, affected groups, data provenance, target, error costs, segment performance, uncertainty, explanation, human oversight, appeal, monitoring, security, privacy, and authority. Aggregate accuracy can conceal unequal or dangerous errors.

Distinguish training, evaluation, and production populations. Define thresholds with sample conditions, drift, retraining, rollback, and model/data versions. Human review works only when reviewers have time, evidence, authority, and a route to disagree. NIST's AI Risk Management Framework organizes governance, mapping, measurement, and management across the lifecycle [3].

### Worked example - triage, not denial

A claims model routes cases needing specialist review. It cannot deny claims, must meet recall targets for high-harm cases by relevant group, exposes uncertainty, and logs its version. Monitoring covers drift, overrides, missed-harm sampling, queue impact, and appeals. Expansion needs a new decision.

AI behavior can change because models, prompts, data, external services, or user populations change. Version all material components, monitor real-world performance and impact, and define triggers for restriction, rollback, retraining, or withdrawal. NIST's current AI RMF 1.0 organizes risk work around Govern, Map, Measure, and Manage; it is voluntary and is under revision, so the applicable framework and version must be recorded.

## BA-03-C06-T06 - Security

### Concept

Security requirements protect confidentiality, integrity, availability, authenticity, accountability, and resilience according to threats and business impact. "The system must be secure" is not verifiable and transfers unresolved risk to implementers.

### Risk-based requirements

Identify assets, actors, trust boundaries, threats, vulnerabilities, impact, controls, residual risk, and owner. Requirements may cover identity proofing, authentication, authorization, least privilege, session management, encryption, secrets, input handling, logging, alerting, dependency management, backup, recovery, secure configuration, incident response, and data disposal.

State measurable conditions and avoid prescribing technology unless architecture or policy requires it. Define misuse and abuse scenarios alongside normal use. Security controls affect usability, privacy, cost, and operations, so analyze trade-offs without treating essential controls as optional preferences.

### Authority

Security requirements derive from assets, threats, trust boundaries, obligations, and risk decisions. Cover identity proofing, authentication, authorization, least privilege, separation, encryption, keys, secure logging, monitoring, vulnerability response, continuity, and recovery as relevant. A control needs its protected outcome and threat context.

Authorization specifies resource, action, context, delegation, revocation, default denial, and evidence—not merely role names. Error and timing must not reveal sensitive existence. Logs require integrity, access, retention, and minimization. Specialists and accountable owners interpret threats and accept residual exposure.

### Failure analysis - roles without object rules

An administrator can edit every customer because the specification lists screens rather than scopes. The correction separates support, billing, policy, audit, and identity powers; restricts by tenant and assignment; requires elevated approval for irreversible changes; and records reason and evidence.

Security specialists perform threat analysis and assurance. The analyst ensures business context, assets, user journeys, operational impacts, exceptions, and decisions are reflected and traced.

## BA-03-C06-T07 - Privacy

### Concept

Privacy requirements govern how information about people is collected, used, disclosed, linked, retained, corrected, and removed, and how people can understand or exercise applicable rights. Privacy is broader than confidentiality: perfectly encrypted data may still be collected or used without a valid purpose.

### Lifecycle questions

Define purpose, necessity, data categories, affected people, source, lawful or authorized basis as applicable, notice, choice or consent where relevant, access, correction, sharing, cross-border or residency conditions, retention, deletion, de-identification, automated decisions, complaints, audit, and incident response. Apply data minimization and purpose limitation.

Consent is not automatically valid or sufficient, especially where people lack meaningful choice. Legal interpretations vary by jurisdiction and require qualified privacy or legal owners. Requirements should record applicability and decision authority rather than copying generic regulation text.

### Integration

Privacy requirements govern purpose, authority, collection, notice, choice where applicable, minimization, accuracy, access, sharing, retention, deletion, and rights. "Comply with privacy law" is not implementable because obligations vary by jurisdiction, role, purpose, and data category. Specialists determine applicability; requirements make controls observable.

Lineage connects collection purpose to derived fields, analytics, models, exports, backups, and third parties. Deletion addresses copies and legitimate exceptions. Consent, where applicable, needs evidence, granularity, withdrawal, and consequences. Protective defaults should not depend on a hidden setting.

### Worked example - secondary analytics

A support service wants transcripts for analytics, although collection served case resolution. Review identifies categories, authority, minimization, de-identification limits, access, retention, supplier processing, and rights. Authentication secrets and unnecessary free text are excluded.

Privacy affects analytics, logs, testing, monitoring, AI training, support, exports, backups, and retirement. Use privacy impact assessment where required or proportionate and trace mitigations to implementation and evidence.

## BA-03-C06-T08 - Accessibility

### Concept

Accessibility requirements ensure people with disabilities can perceive, operate, understand, and reliably use a digital service, including with assistive technologies. Accessibility is a core quality and inclusion concern, not a cosmetic enhancement deferred until the end.

### Requirement frame

Identify applicable standard and conformance target, user journeys, content types, platforms, input methods, assistive technologies, language, time limits, errors, authentication, documents, media, support, and procurement. W3C recommends WCAG 2.2 as the current Web Content Accessibility Guidelines version; organizational or legal obligations may specify a particular level or additional standard.

Requirements should address keyboard access, focus, structure, labels, alternatives, contrast, reflow, zoom, motion, timing, error identification, status messages, authentication, and consistent interaction as relevant. Do not translate accessibility into a single automated score. Automated checks find only some issues; expert and user evaluation are also needed.

### Inclusive lifecycle

Accessibility requirements support content, interaction, and service across abilities, technologies, environments, and temporary limitations. Reference the applicable WCAG version and level, then specify keyboard, focus, semantics, labels, errors, timing, reflow, contrast, alternatives, authentication, documents, notifications, and assisted channels. Conformance alone can miss the whole journey.

Include disabled users and specialists throughout discovery, design, content, development, testing, procurement, and operations. Automated checks find only some defects. An alternative that is slower, costly, or unavailable at the needed time may remain exclusionary.

### Worked example - identity without a visual-only barrier

An identity flow requires distorted characters and face matching. Revised requirements provide accessible bot protection, equivalent recovery when biometrics fail, keyboard and screen-reader operation, sufficient time, clear errors, and assisted service. Fraud control remains without treating one ability as legitimacy.

Include disabled people in discovery and evaluation with accessible participation and compensation where appropriate. Preserve accessibility through content changes, third-party components, updates, support, and incident handling. An alternative channel is not equivalent if it is slower, more expensive, stigmatizing, or unavailable.

## Integrated digital requirements model

A decision service may receive applications through APIs, publish governed reports, provide operational dashboards, automate low-risk checks, and use an AI model to flag cases for review. The requirement set must preserve shared data definitions, access and error behavior, human responsibility, monitoring, privacy, security, and accessibility across every channel. Transition requirements cover migration, training, fallback, and retirement; traceability connects each digital behavior to stakeholder and business outcomes.

Digital topics overlap. API logs affect privacy; dashboard refresh affects operational decisions; AI monitoring requires data; security controls affect accessibility; automated exceptions affect staffing. Treating them as separate checklists misses these interactions.

### Boundary-to-operation method

Begin with the outcome, users, affected non-users, and system boundary. Map external actors, trust zones, information flows, decisions, states, and critical dependencies. For each interaction, specify normal behavior and quality, then examine invalid input, duplicate events, unavailable dependencies, unauthorized action, partial completion, recovery, monitoring, and retirement. This creates a connected model instead of eight isolated lists.

| Digital concern | Required control focus | Typical evidence |
|---|---|---|
| API | Contract meaning, compatibility, failure and idempotency | Contract tests, consumer verification, traces |
| Report | Governed measures, population and reconciliation | Definition review, source reconciliation, sample outputs |
| Dashboard | Decision use, freshness and accessible interpretation | User evaluation, lineage, accessibility test |
| Automation | Authority, exceptions, audit and recovery | Scenario tests, queue reconciliation, rehearsal |
| AI | Intended use, error distribution, oversight and drift | Evaluation report, monitoring, appeal evidence |
| Security | Threat-based prevention, detection and recovery | Review, testing, logs, recovery exercise |
| Privacy | Purpose, minimization, rights, retention and sharing | Data map, specialist review, rights tests |
| Accessibility | Inclusive end-to-end task completion | WCAG evaluation and user evidence |

### Worked example - integrated application decision

An application service accepts data through web and assisted channels, calls identity and eligibility APIs, uses an AI model only to route complex cases, records a rule-based decision, notifies the applicant, and feeds reporting. Shared semantics and correlation span channels. API timeouts create recoverable state rather than duplicates. Security limits staff action; privacy constrains model features and retention; accessibility provides equivalent evidence submission; dashboards expose delay without revealing personal records.

Operations rehearse dependency failure and queue recovery. Testers verify rule boundaries and contracts. Model evaluators examine routing errors by relevant group. Privacy and security reviewers inspect lineage and logs. Accessibility evaluation covers the full journey, including errors and notification. Release considers combined evidence because each component can pass locally while the service fails end to end.

Quality attributes create trade-offs requiring authority. Extensive logging can aid security investigation while violating minimization. Aggressive timeouts protect capacity while excluding poor connections. Strict authentication can reduce takeover while creating inaccessible recovery. Specialists and owners compare options and accept residual risk; generic "best practice" wording does not resolve the tension.

Operational requirements complete the specification. Define service ownership, support, alerts, escalation, capacity, backups, restoration, reconciliation, supplier response, configuration, and controlled change. A happy-path demonstration is insufficient. Readiness means the organization can operate, observe, recover, support, and govern the capability.

Transition requirements identify data migration, parallel operation, cutover, training, communications, temporary controls, rollback, reconciliation, and retirement. A replacement API may be technically available while consumers still depend on old semantics. A dashboard may calculate correctly while teams have not agreed how to respond. A model can meet evaluation thresholds while monitoring and appeal are absent. Transition closes the distance between implemented behavior and an operable service.

Observability must be specified without turning every event into unrestricted surveillance. Define events, measures, correlation, access, retention, alert thresholds, and diagnostic purpose. Logs should enable reconstruction of critical decisions without storing unnecessary secrets or personal content. Synthetic checks, health signals, business reconciliation, and user feedback reveal different failures. No single green status proves the service outcome.

Digital requirements evolve with dependencies and evidence. Interface deprecation, rule changes, new threats, model drift, accessibility findings, supplier incidents, and privacy decisions can reopen the baseline. Stable identifiers and typed trace links allow impact analysis. The change authority considers compatibility, transition, affected users, operational risk, and evidence rather than updating a local specification in isolation.

## Common misconceptions

- An API contract is more than endpoint names and payload examples.
- A report mock-up does not define data meaning or lineage.
- A dashboard is not improved by adding more metrics.
- Automation does not remove accountability.
- AI accuracy does not establish fairness, safety, or suitability.
- Security is not one generic non-functional statement.
- Privacy is not identical to secrecy or consent.
- Automated accessibility testing cannot establish full conformance.

## Ethics, limitations, and professional boundaries

Digital systems can scale exclusion and harm. Identify affected people, misuse, unequal error, inaccessible routes, surveillance, and irreversible outcomes early. Make escalation, human review, appeal, fallback, monitoring, and retirement requirements explicit. Analysts coordinate business meaning and trace decisions but must involve authorized specialists for security, privacy, accessibility, legal, safety, statistical, and AI assurance.

## Advanced synthesis

High-quality digital requirements describe an accountable operating system, not a collection of features. They join semantics, behavior, quality, data, controls, people, evidence, change, and retirement. The most important requirement may be a boundary: where automation must stop, when a result cannot be used, which data must not be collected, or when the service must fall back safely.

### Contract and semantic integrity

Digital components fail at their seams. Two systems can conform to the same field schema while interpreting a status, timestamp, customer, or amount differently. Interface requirements therefore link technical types to governed business definitions, lifecycle states, precision, provenance, and authority. Consumer-driven examples help reveal misunderstandings, but shared examples do not replace an authoritative semantic contract. When meaning changes, compatibility analysis must examine stored data, historical messages, caches, reports, and delayed consumers.

API security is similarly behavioral. OWASP's API risk guidance highlights authorization, authentication, resource consumption, inventory, and unsafe consumption concerns [4]. Translating those concerns into requirements means specifying which actor can perform which action on which object, how ownership and tenant boundaries are enforced, what happens under enumeration or excessive demand, how abandoned versions are retired, and how third-party data is validated. "Use secure APIs" provides none of this evidence.

### Data and decision integrity

Reports, dashboards, automation, and AI often reuse the same data while applying different transformations. A controlled information model names source events, derived measures, quality rules, late-arriving behavior, corrections, and lineage. Decision logic identifies the rule or model version used for each result. Without that record, an organization cannot explain why a customer received an outcome or reproduce a historical report after definitions change.

Data quality should be connected to use. Completeness, accuracy, validity, timeliness, uniqueness, and consistency have different consequences for different decisions. A missing optional preference is not equivalent to a missing payment amount. Requirements define critical elements, thresholds, detection, quarantine, correction authority, and downstream behavior. Silently substituting a default may improve a completeness metric while corrupting meaning.

### Worked example - preventing silent decision drift

An eligibility service consumes income from three channels. One sends annual gross income, one sends monthly net income, and one leaves the period implicit. All values pass a numeric schema, but decisions diverge. The corrected contract requires amount, currency, period, gross/net basis, evidence date, source, and confidence; rejects ambiguous submissions; and records the normalized calculation with its rule version. Reports disclose unresolved and manually corrected cases rather than hiding them in an average.

### Resilience and recovery

Availability requirements need a service boundary, population, window, exclusions, source, and consequence. A technically available API can still be unusable if dependencies time out or data is stale. Resilience scenarios cover degraded mode, backlog growth, duplicate delivery, partial commits, region or supplier failure, restoration, and reconciliation. Recovery time and recovery point objectives must connect to business tolerance and the state that can actually be restored.

Design for safe uncertainty. After a timeout, the caller should not guess whether an irreversible command succeeded. After failover, the service should detect replay and preserve ordering where it matters. After restoration, reconciliation should compare authoritative business totals or states, not just infrastructure health. Manual fallback needs capacity, instructions, access, evidence, and an exit path; an untested fallback is an assumption.

### Human responsibility in digital operation

Automation changes work rather than eliminating it. Requirements should identify who monitors, handles exceptions, corrects data, responds to alerts, approves overrides, supports users, and owns performance. Work queues expose priority, age, reason, service commitment, and escalation without disclosing unnecessary data. Overrides record rationale and are reviewed for patterns; a rising override rate may indicate rule or model failure rather than staff noncompliance.

Human oversight must be realistic. A reviewer presented with hundreds of opaque recommendations under time pressure is a rubber stamp. Effective oversight specifies which cases require review, what evidence is available, what alternatives can be selected, how disagreement is recorded, and how harmful patterns trigger suspension. Training and procedures support the role, but authority and system behavior must also permit meaningful intervention.

### Assurance as connected evidence

Release assurance combines functional tests, contract tests, reconciliation, performance measurement, security evaluation, privacy review, accessibility evaluation, operational rehearsal, and outcome monitoring according to risk. Passing one category cannot compensate for an unrelated failure. A load test does not prove authorization; a standards scan does not prove a disabled person can complete the journey; model accuracy does not prove lawful data use.

Evidence remains linked to item and version. Test environments, datasets, configurations, assumptions, exceptions, and dates matter. Production measures validate behavior under real conditions but may expose users to harm if safeguards are absent. Use pilots, feature controls, monitoring, rollback, and limited populations when uncertainty warrants them. The decision authority sees both successful evidence and unresolved limitations.

### Sustainable change and retirement

Every interface, report, dashboard, automation, model, control, and accessibility workaround creates ongoing ownership. Requirements name review cadence, dependency support horizon, data retention, deprecation notice, migration assistance, and retirement evidence. An obsolete API left reachable becomes security and consistency risk. An unused dashboard can keep distributing personal data. A retired model may remain necessary to explain historical decisions.

Sustainability also includes computational and operational cost where material. High-frequency refresh, redundant storage, unnecessary model complexity, and verbose logging consume resources. These costs should be evaluated alongside decision value, reliability, security, privacy, and user need. Efficiency is not a license to reduce accessibility or assurance; it is another explicit design constraint with an owner and measure.

The mature requirements set is therefore a governed service model. It describes what the digital system must do, what it must never do, how people remain accountable, what evidence demonstrates acceptable behavior, how failure is contained and recovered, and how change is controlled. That model allows teams to choose technology without losing business meaning or human consequence.

Procurement does not transfer these responsibilities. When a supplier provides an API, platform, model, identity service, or analytics product, the acquiring organization still defines its outcome, integration boundary, data use, assurance needs, support, exit, and accountability. Contract terms should address service levels, incident notification, vulnerability handling, accessibility evidence, subprocessors, data return and deletion, change notice, audit rights, and transition assistance according to risk.

Build-versus-buy analysis should compare the full operating model rather than feature lists. A configurable product may shorten delivery while limiting rule transparency or historical reproduction. A managed AI service may reduce infrastructure work while constraining evaluation and appeal. Requirements expose these consequences early enough for a commercial and technical decision. After acquisition, configuration, extensions, user workflows, and local data remain subject to the same integrated validation and control as custom development.

Ownership remains explicit.
